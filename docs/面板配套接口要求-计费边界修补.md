# V2bX 计费边界修补：给面板维护 agent 的配套要求

日期：2026-10-29。后续状态更新：能力接口已按用户授权实现并部署到蓝绿，面板独立本地提交 `3cff0a3`；正式 HTTP 认证/禁用态、进程隔离启用态及 V2bX 客户端联调通过。正式全局开关仍关闭，源站未部署；本文的小数倍率配套要求仍待实现。节点新修补仅本地提交。旧九项修复已推送独立修复分支，未合并 main 或发布。

## 1. 新增经过认证的节点能力接口

`GET /api/v1/server/UniProxy/traffic_capabilities`

沿用现有 token、node_type、node_id，执行相同的认证与节点权限检查。必须返回该节点实际获准使用的能力，不能用未经节点白名单检查的全局配置冒充。

```json
{"data":{"version":1,"enabled":true,"durable_ack":true,"deduplication":true,"receipt_retention_seconds":0}}
```

- `version=1`：现有持久批次请求/确认协议。
- `enabled=true`：该节点已允许批次模式。
- `durable_ack=true`：HTTP 200 前，收据已经持久保存；队列失败仍能恢复处理。
- `deduplication=true`：重复请求、重复作业、丢确认重放、进程重启不会重复入账。
- `receipt_retention_seconds=0`：永久保留去重身份及摘要，**不是立即删除**。载荷在应用后可清理；身份、摘要、应用状态不能随意清理。

新节点会在启动入站前调用此接口。缺失、关闭、字段不完整、版本未知、有限保留期均拒绝批次模式启动，进程退出非零；不会自动退回旧上报。节点未开启批次模式时保持旧接口兼容，明确提示其失联风险。

有限保留期需要另行设计“节点持久过期状态/双方确认退休”协议，否则旧磁盘批次可能在面板忘记去重记录后重复扣费。本轮不支持这种组合。

## 2. 保持批次请求和确认约定

- 地址仍为 `POST /api/v1/server/UniProxy/push`。
- 头 `X-Traffic-Batch-ID`，32 位小写十六进制随机 ID。
- 正文仍为数字用户 ID 到 `[upload,download]` 的映射；字节数为非负整数。
- 去重唯一键为实际存储节点类型、节点 ID、批次 ID；保留 AnyTLS 与面板存储类型映射兼容。
- 同 ID、同规范化载荷：返回相同确认，不再扣费。
- 同 ID、不同载荷：409，不覆盖原收据、不再次扣费。
- 正确确认：HTTP 200，`{"data":true,"batch_id":"原请求的批次ID"}`。
- 对用户扣量和收据标记应用必须在同一事务；作业重复执行安全。
- 必须具备待应用收据恢复命令/调度及积压告警。节点收到确认只表示面板已持久承担处理责任，不要求所有队列作业已完成。

## 3. 本轮发现的兼容性阻断：小数倍率逐批舍入

蓝绿真实数据库、隔离账号、外层事务回滚实验：

- 倍率 0.5，两个独立的 `[1,1]` 批次：实际上传/下载各增加 2。
- 倍率 0.5，一个 `[2,2]` 批次：实际上传/下载各增加 1。

两组原始流量完全相同，账单不同。现有整数列与逐批更新的舍入会让批次划分影响扣量；不能把偶数字节的精确对账外推为任意倍率/批次都等价。节点通过聚合检查点、共用封存周期避免无谓拆批，但无法独自修正面板舍入。

建议面板方案（由用户与面板 agent 确认最终计费规则）：

1. 使用精确十进制或定点整数解析倍率，避免二进制浮点累积。
2. 为用户上传、下载分别保存小数余量。每次计算“旧余量 + 本批字节 × 倍率”，将整数部分计入用量，小数部分留给后续批次。
3. 用量、余量和收据应用状态必须在同一事务、同一锁序下更新。重复作业不能重复增加余量。
4. 明确倍率取值时点。本轮仍沿用收据接收时的节点倍率快照，未改为采样时倍率。
5. 明确账号流量重置、套餐重置、删除、迁移时余量如何处理；新规则不追溯改写历史用量。
6. 确认余量按用户聚合还是按用户/节点维度保存；要实现跨节点划分不影响总账，通常需要最终在用户维度汇总。

**上线前必须解决并验收该问题，或者由用户明确接受现有逐批舍入差异。** 当前能力门禁检查持久确认与去重，不会自动推断面板的小数舍入正确性。不要只新增能力接口返回 true，就宣称整个计费兼容性已完成。

## 4. 面板验收矩阵

- 整数及小数倍率，奇数/偶数字节；同一总流量合并或随机拆成多个批次，最终用量与余量一致。
- 多节点不同倍率、同用户并发写入；倍率变更前后保持约定。
- 已保存未入队、已入队未应用、应用事务回滚、应用成功后丢确认、重复作业与 HTTP 重放。
- 长期积压恢复、队列恢复扫描、节点重启及旧单批次文件迁移。
- HTTP 200 前必须持久，错误确认不让节点删除批次；未知节点/凭据没有能力信息或写权限。

## 5. 本轮验证边界

本节以下描述较早的四项节点修补验收。后续接口专项实测已使用蓝绿正式 Nginx/FPM 接口；启用态通过独立进程加载真实 Laravel 路由/控制器，不伪造响应。真实令牌验证限蓝绿本机，VPS 使用隔离进程合成令牌。新增接口方法、CPU/内存和清理记录见面板提交 `3cff0a3` 中 `docs/traffic-capabilities-bluegreen-20261029.md`。该专项没有重新进行计费写入，也未修复小数倍率问题。

跨机测试通过私有适配器模拟能力响应，实际流量接收、收据、作业和数据库使用蓝绿已有实现；假队列，不消费共享队列、不发邮件。它证明节点协议检查与已有持久计费路径可联调，不代表面板新接口已经实现，也不代表现有小数倍率问题已修。

节点默认旧模式、尚未落盘的最后检查点、磁盘满/故障期间保留在内存的计数，仍有明确风险。安装脚本不自动启用新模式；发布/升级前需节点能力检查、私有持久目录、积压文件迁移及回滚检查。新队列版本不能直接用旧二进制读取。
