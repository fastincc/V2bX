# Checkpoint lock isolation

Slow reliable-journal persistence must not hold a core's authentication or accounting-identity lock. Each core now prepares an immutable attribution/counter snapshot under its short identity lock, saves outside that lock, and subtracts only the successfully saved sample. Data-plane increments continue during the save. A failed or ambiguous save retains the counters and the existing journal failure/poisoning policy.

A reference-counted node gate covers snapshot consumers, legacy reset sampling, reaping, node creation/removal, drain/resume and whole-core close. Always acquire the gate before core locks. Ordinary authentication, traffic I/O and user revocation do not acquire it. The gate keeps original counter references reachable through completion even when users are revoked or re-added; another node can sample independently. Gate entries are removed when their last holder/waiter leaves. Whole-core close intentionally waits for outstanding node operations.

Configuration, real-IP handling, audit fields, device policy, panel APIs, upload/download direction, checkpoint frequency, batch IDs and on-disk queue format are unchanged. No added packet-level synchronization, timer reduction, skipped fsync or unbounded asynchronous write queue is used. Snapshot preparation still scales with the number of counters; disk and CPU resource contention are not eliminated.

Validation covers slow callbacks, same-node and cross-node admission, concurrent increments and reset sampling, Hy2 revocation/re-addition while saving, failed persistence, lifecycle waiting, identity attribution, and gate cleanup. Existing protocol, tail accounting and reliable-delivery tests remain applicable.

The opt-in `TestCheckpointTransportProfile` runs local real TLS/AnyTLS with PROXY v2, structured access audit, production routing/leased counters and a private durable queue. Set `CHECKPOINT_PROFILE_DURATION=5s`, `CHECKPOINT_PROFILE_PARALLEL=1` or `8`, and optionally `CHECKPOINT_PROFILE_SLOW_MS=300`. It reconciles both traffic directions and reports throughput, first-exchange latency, process CPU, peak RSS and post-GC heap. Slow mode deliberately checkpoints every 100ms; normal mode uses one second. This is a loopback comparison, not WAN capacity or production validation.

Local acceptance (2026-10-31, macOS arm64): targeted race tests passed five rounds; the related common/limiter/API/config/node/core/command race suite passed. Thirty serial baseline/candidate profiles used matched real-IP/audit/durable-store settings and reconciled exactly. Normal 8-worker confirmation (three alternating 10-second runs per version) had median aggregate throughput 2799.38 -> 2802.39 MiB/s and first-exchange P99 0.237 -> 0.239ms, with differences changing sign across rounds. Under deliberately injected 300ms checkpoint delay, the three 5-second 8-worker runs had median P99 309.732 -> 0.235ms. These loopback echo rates include both traffic directions and are not external network speeds. Initial profile setup was rejected by private-directory validation; the fixture was corrected to let the store create a private subdirectory before these measurements.
